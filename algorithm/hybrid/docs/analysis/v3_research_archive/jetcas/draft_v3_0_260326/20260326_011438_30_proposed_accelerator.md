## V. THE PROPOSED HBTXR ACCELERATOR

### A. Hardware Architecture

To make HBTXR practical for on-device XR systems, we design a dedicated FPGA accelerator that is co-optimized with the proposed hybrid tracking algorithm. The accelerator is organized as a heterogeneous **CPU-FPGA** system in which the CPU handles sensor interfacing and high-level runtime control, while the FPGA executes the latency-critical neural inference pipeline. This partition is motivated by the complementary characteristics of the workload: hybrid eye tracking contains both irregular control logic, such as mode switching and recovery handling, and highly regular tensor computation, such as token embedding, transformer inference, and dense head prediction.

Fig. 2 illustrates the overall hardware architecture. The FPGA side consists of four major components: 1) **input staging and tokenization**, 2) a shared **transformer engine**, 3) lightweight **task-specific head engines**, and 4) an **FSM-based runtime controller**. Frame patches and event representations are transferred from the host to on-chip buffers through a DMA interface. The tokenization front-end converts the frame and event inputs into patch embeddings compatible with the shared Partial DeiT-Tiny backbone. The resulting tokens are forwarded to the transformer engine, and the encoded features are then consumed by the Search, Track, and Mask heads. A control FSM manages execution order, buffer reuse, and mode-specific branching.

A key design principle of the accelerator is **feature reuse across hybrid modes**. Search and Track share the same backbone, and therefore the accelerator is designed around a common latent feature path rather than separate frame and event inference pipelines. In particular, when the system remains in Track mode, the frame branch does not need to be recomputed at every iteration. Instead, the accelerator reuses cached frame-side features and processes only the newly arrived event tokens together with the persistent shared representation. This reduces both on-chip memory traffic and external bandwidth, which is essential for sustaining sub-millisecond latency.

The architecture also reflects the algorithmic asymmetry between Search and Track. Search requires broader spatial coverage and more robust relocalization, whereas Track requires frequent low-latency local updates. Accordingly, the accelerator supports two execution profiles under a unified datapath: a **full-search profile**, which refreshes the frame-event representation and invokes the Search and Mask heads, and a **low-latency tracking profile**, which prioritizes incremental event-driven refinement with minimal control overhead. This unified-yet-adaptive structure is the central hardware counterpart of the proposed HBTXR algorithm.

### B. Transformer Engine

The transformer engine is the computational core of the HBTXR accelerator. It implements the shared Partial DeiT-Tiny backbone used by both Search and Track modes and is designed to efficiently support multimodal token processing under strict latency constraints. Rather than treating the frame branch and the event branch as independent networks, the engine operates on a fused token sequence produced by the shared tokenization front-end. This design allows the same encoder to jointly model semantically stable frame cues and temporally responsive event cues.

At the block level, each transformer stage is decomposed into four pipeline units: 1) linear projection for query, key, and value generation, 2) attention score computation and accumulation, 3) weighted feature aggregation, and 4) feed-forward transformation. These units are connected through on-chip buffers so that intermediate activations remain local to the accelerator. As a result, repeated off-chip memory access for token features is avoided. Since the backbone is shared across all downstream heads, the encoded feature sequence is written once to the feature buffer and then broadcast to the Search, Track, and Mask head engines as needed.

To further improve efficiency, the engine supports **streaming-based feature reuse**. During Track mode, the frame-side latent context changes slowly relative to the event stream. Therefore, the accelerator caches the reusable portion of the encoded representation and updates only the event-dependent path at each tracking step. This mechanism substantially reduces redundant computation during high-rate tracking. By contrast, when the system enters Search mode, the frame context is refreshed and the full fused encoding path is recomputed. In this way, the transformer engine preserves semantic robustness during recovery while maintaining low steady-state latency during tracking.

The head engines are intentionally lightweight. The Search head performs coarse relocalization from the shared latent sequence, the Track head predicts local residual displacement, and the Mask head produces dense pupil support for geometric validation. Because these heads are decoupled but operate on a common encoded feature tensor, they can be mapped to compact task-specific datapaths without duplicating the expensive backbone computation. This organization is particularly suitable for FPGA deployment, where preserving compute density and avoiding duplicated control logic are both important.

### C. FSM-Based Runtime Scheduler

Although the high-level Search/Track policy is decided on the host side, low-overhead execution on FPGA requires a dedicated hardware scheduler that can autonomously orchestrate mode-specific inference steps. For this purpose, HBTXR employs an **FSM-based runtime scheduler** inside the accelerator. The scheduler translates host-issued mode commands into cycle-level execution sequences, manages buffer validity, and minimizes unnecessary pipeline reconfiguration.

The FSM operates over a small set of execution states, including `IDLE`, `LOAD`, `TOKENIZE`, `ENCODE`, `SEARCH_HEAD`, `TRACK_HEAD`, `MASK_HEAD`, `REFINE`, and `WRITEBACK`. In Search mode, the scheduler loads both frame and event inputs, refreshes the shared token representation, runs the full transformer backbone, invokes the Search and Mask heads, performs geometry-aware refinement, and returns the relocalized pupil state to the host. In Track mode, the scheduler skips full frame refresh when the cached frame context remains valid, loads only the latest event representation, reuses the stored features, runs the Track and Mask heads, and writes back the refined local update. Thus, the FSM enforces different execution paths for Search and Track while keeping the datapath itself largely shared.

This control structure is important for two reasons. First, it reduces host intervention overhead. The CPU is not required to micromanage every accelerator stage; it only provides the operating mode, control thresholds, and input pointers, while the FPGA-side FSM handles the detailed sequencing. Second, it aligns naturally with the semantics of the proposed algorithm. Search corresponds to a recovery-oriented execution path with broader processing scope, whereas Track corresponds to a fast incremental path with aggressive reuse. The FSM therefore serves as the hardware realization of the algorithmic search-track decomposition.

In addition, the scheduler maintains status flags related to cache validity, mask confidence, and output readiness. These flags are used to synchronize the accelerator with the host-side controller and to ensure that state transitions are performed safely. As a result, the entire system supports deterministic and low-overhead runtime switching, which is necessary for stable operation in XR workloads with rapidly changing eye motion patterns.

### D. CPU-FPGA Workload Partition

The proposed HBTXR system adopts a workload partitioning strategy that assigns irregular control and system orchestration to the CPU, and dense data-parallel inference to the FPGA. This partition is chosen to maximize end-to-end responsiveness while keeping the design practical for embedded XR platforms.

The **CPU** is responsible for sensor acquisition, timestamp alignment, frame/event packaging, high-level Search/Track mode selection, and final application-side post-processing such as gaze mapping and system integration. These tasks contain branching logic, device management, and runtime exceptions that are more naturally handled in software. The CPU also determines whether relocalization is required based on the confidence signals returned by the accelerator.

The **FPGA**, in contrast, executes all latency-dominant tensor operations, including patch embedding, multimodal token fusion, transformer inference, decoupled head execution, and geometry-aware local refinement. These stages are regular, streaming-friendly, and repeatedly executed, making them well suited for dedicated hardware acceleration. In Track mode, the FPGA additionally exploits cached frame features and event-driven incremental updates to reduce both compute and communication cost.

Under this partition, the end-to-end latency may be expressed as
\[
T_{\mathrm{e2e}} = T_{\mathrm{host}}^{\mathrm{prep}} + T_{\mathrm{transfer}} + T_{\mathrm{fpga}}^{\mathrm{infer}} + T_{\mathrm{host}}^{\mathrm{post}},
\]
where \(T_{\mathrm{host}}^{\mathrm{prep}}\) denotes host-side preprocessing and scheduling overhead, \(T_{\mathrm{transfer}}\) denotes data movement between host and FPGA, \(T_{\mathrm{fpga}}^{\mathrm{infer}}\) denotes accelerator execution time, and \(T_{\mathrm{host}}^{\mathrm{post}}\) denotes lightweight output handling. The design objective of HBTXR is to minimize not only \(T_{\mathrm{fpga}}^{\mathrm{infer}}\), but also the combined overhead induced by frequent mode switching and repeated feature movement. This is precisely why the proposed system couples search-track logic, feature reuse, and hardware scheduling within a unified design.

The proposed CPU-FPGA partition also improves scalability. Search-mode execution can be invoked only when necessary, while Track-mode execution dominates steady-state operation. Consequently, the system allocates computation according to runtime demand rather than enforcing a fixed full-cost inference path at every step. This makes HBTXR particularly suitable for practical on-device XR scenarios, where sustained low latency and efficient resource usage are both required.

In summary, the proposed accelerator architecture is not merely an implementation target for the HBTXR model. Instead, it is a co-designed runtime substrate that directly reflects the structure of the hybrid algorithm: shared multimodal encoding, decoupled search/track execution, feature reuse, and explicit runtime state control. The following section evaluates this design in terms of both algorithmic performance and accelerator efficiency.
