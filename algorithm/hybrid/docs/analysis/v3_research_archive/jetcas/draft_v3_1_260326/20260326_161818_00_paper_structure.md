## 1. HG-PIPE 핵심 아이디어 분석

HG-PIPE에서 직접 가져와야 하는 것은 구현 세부가 아니라 아래 5개 설계 원리다.

- `1)` 순수 temporal engine은 메모리 왕복이 크고, 순수 full pipeline은 글로벌 dependency 때문에 비효율이 생긴다.
- `2)` 따라서 연산마다 같은 granularity를 쓰지 말고, dependency와 locality에 따라 다른 granularity를 섞어야 한다.
- `3)` 전역 동기화가 필요한 구간은 phase-level로, locality가 좋은 구간은 tile/stream-level로 처리해서 버퍼 비용과 idle gap을 함께 줄인다.
- `4)` nonlinear operator는 별도 근사 유닛이나 lookup-driven 처리로 비용을 줄인다.
- `5)` 데이터플로우와 병렬도는 알고리즘 구조와 함께 설계해야 한다. 즉, accelerator는 모델 뒤에 붙는 것이 아니라 모델 구조에 맞춰 설계된다.

이 논문에서 HBTXR에 특히 유효한 부분은 다음이다.

- Search와 Track은 workload 성격이 다르다.
- Search는 global refresh, Track은 local incremental update다.
- shared backbone이 있으므로 full recomputation path와 reuse-heavy path를 분리할 수 있다.
- 따라서 HBTXR 하드웨어는 `하나의 균일한 pipeline`보다 `mode-aware mixed-granularity architecture`로 설명하는 편이 훨씬 설득력 있다.

반대로 그대로 가져오면 어색한 부분도 있다.

- ViT 전체를 대상으로 한 generic operator taxonomy
- quantization/LUT approximation을 논문의 주기여처럼 전면화하는 것
- CNN/ViT accelerator와 동일한 benchmarking language
- pure throughput-oriented framing

HBTXR은 generic ViT accelerator paper가 아니라 `hybrid eye-tracking system paper`여야 한다.

## 2. HBTXR 하드웨어 파트에 적용할 설계 원리

HBTXR 쪽 하드웨어 섹션에는 HG-PIPE의 원리를 아래처럼 바꾸어 적용하는 것이 맞다.

- Search path는 `refresh-oriented execution path`
- Track path는 `state-persistent incremental path`
- 둘을 같은 하드웨어에서 처리하되, granularity를 다르게 가져간다.
- backbone은 공유하되, Track에서는 feature/state reuse를 극대화한다.
- global dependency가 있는 attention/fusion 단계는 coarse phase 단위로,
- head execution이나 일부 token/state update는 stream/tile 단위로 설명한다.
- 핵심 병목은 “self-attention 일반론”이 아니라 `frame-event fusion + search/track mode switch + feature reuse`로 다시 정의해야 한다.

즉, HBTXR 하드웨어 섹션의 중심 문장은 이렇게 잡는 편이 좋다.

- `HBTXR adopts a mode-aware mixed-granularity execution architecture that maps refresh-heavy search and reuse-heavy tracking onto a shared transformer-oriented accelerator.`

이 문장은 HG-PIPE의 냄새는 줄이면서도 핵심 철학은 유지한다.

## 3. 베낀 느낌을 줄이기 위한 용어 치환

| HG-PIPE 계열 표현 | HBTXR에 권장하는 표현 | 사용 맥락 |
|---|---|---|
| Hybrid-Grained Pipeline | `Mixed-Granularity Execution Architecture` | 섹션 제목, 전체 하드웨어 개념 |
| Coarse-Grained Pipeline | `Phase-Level Execution Path` | attention/fusion/global sync 구간 |
| Fine-Grained Pipeline | `Tile-Stream Execution Path` | head/update/reuse 구간 |
| Pipeline Bubbles | `Inter-Stage Idle Gaps` | 스케줄링 비효율 설명 |
| PIPO Buffer | `Refresh Buffer Pair` | Search path의 full refresh 버퍼 |
| FIFO Buffer | `Streaming Token Queue` | Track path의 streaming 경로 |
| Output-Stationary Dataflow | `Accumulation-Resident MatMul Flow` | MM engine 설명 |
| LUT-based Approximation | `Table-Assisted Nonlinear Unit` | activation/rsqrt/exp 근사 설명 |
| Global Dependency | `Cross-Token Synchronization Constraint` | attention/fusion 설명 |
| Hybrid-Grained Features | `Mode-Adaptive Overlap Strategy` | timeline figure 설명 |

주의할 점도 있다.

- `quantization`, `LUT approximation`, `operator fusion`은 실제 구현 근거가 약하면 “optional implementation path”로 내리는 것이 맞다.
- HBTXR 논문에서는 `mixed-granularity`, `mode-aware`, `reuse-oriented`, `shared-backbone` 이 네 단어가 중심 어휘가 되어야 한다.
