# Runtime-Mode Full AXI Weight Path Evidence - 2026-06-28

## Goal

Restore the learned-parameter path for the runtime Search/Track E2E AXIS top, make the QKV/MLP weight source explicit, remeasure Search/Track latency, and keep fastpath latency separate from full-model latency.

## Selected Parameter Path

Current selection: AXI weight path.

- Conv/Head learned parameters are restored by using the existing non-fastpath E2E datapath.
- QKV/MLP weights are selected as external `m_axi` reads through `gmem_e2e_weights`.
- ROM/BRAM/URAM is not selected as the persistent full-model weight store in this profile.
- BRAM/URAM/LUTRAM are still used for internal caches, activations, score buffers, and math LUTs generated by HLS.

Reason: the non-fastpath AXI implementation already exists and compiles against the packed weight interface. A ROM/BRAM/URAM persistent-weight profile would require a separate codegen/static-array flow and fresh capacity analysis before it can be treated as the canonical learned path.

## Active Block And Path

Search mode:

1. AXIS frame read: Search uses the larger frame/control shape.
2. Learned patch/conv embedding: `hgtxr_conv_patch_embedding`.
3. Global buffer load.
4. Shared controller: repeated weighted ATTN and MLP blocks through `hgtxr_e2e_controller_run`.
5. Learned state head: `hgtxr_e2e_mlp_head`.
6. AXIS state write.

Track mode:

1. AXIS frame read: Track uses the smaller frame/control shape.
2. The same learned patch/conv embedding.
3. The same global buffer and controller datapath.
4. Fewer active tokens / lower depth selected at runtime.
5. The same learned state head.
6. AXIS state write.

The physical blocks are shared; the runtime mode changes active token count, frame shape, and depth limit.

## Next Optimization Plan

1. Split or cache hot weight reads so layernorm gamma/beta and QKV/MLP loads do not serialize through one AXI port.
2. Decide whether QKV/MLP persistent weights should move from AXI to URAM/BRAM for the target model size, then run a capacity check before implementation.
3. Re-run full AXI csynth after weight-path optimization.
4. Only after HLS latency approaches the 4 ms / 1 ms targets, run full AXI Vivado route and power.
5. Run board Search/Track latency with imported JSON samples to obtain p95/p99 and DMA bandwidth.
