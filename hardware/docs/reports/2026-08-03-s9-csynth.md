# S9 — csynth · 자원 · 타이밍

**V1 이 여덟 단계 동안 못 보던 것을 첫 csynth 가 즉시 냈습니다.** 값이 맞는 것과
그 값이 의도한 하드웨어에서 나오는 것은 다른 주장이고, g++ 는 두 번째를 검사할 수 없습니다.

```bash
sh hardware/build/run_csynth.sh                 # 유닛 16개
python3 hardware/tools/report_csynth.py         # 자원 · 타이밍 · II
```

환경: WSL `Ubuntu2404`, `/tools/Xilinx/Vitis_HLS/2023.2`, 파트 `xczu7ev-ffvc1156-2-e`
(ZCU104), 주기 **3.333 ns**. 아래는 전부 **csynth 추정치**입니다 — Vivado 배치배선 후 숫자가
아닙니다.

## 3. csynth 가 잡은 것 — V1 이 볼 수 없던 것

### 3-1. 클래스 스코프 `#pragma HLS` 는 적용된 적이 없습니다

첫 csynth 의 첫 에러입니다.

```
ERROR: [HLS 207-5512] '#pragma HLS' is only allowed in function scope
  (hardware/module/include/hbtxr_rmu.hpp:51)
  (hardware/module/include/hbtxr_smu.hpp:57)
```

`HbtxrRmu::weight` 와 `HbtxrSmu::bt` 의 `array_reshape` 가 **멤버 선언 옆**에 있었습니다.
툴은 거부하고, g++ 는 `-Wno-unknown-pragmas` 로 조용히 버립니다. 즉 SPEC §2-A 의
**"세 숫자가 일치해야 한다"(스트림 폭 · 언롤 · reshape) 중 하나가 S2~S8 여덟 단계 내내
툴에 닿은 적이 없었습니다.**

배열을 만지는 **멤버 함수마다** 다시 적어서 해결했습니다. 이후 `compute` 의 `reduce` 가
II=1 로 스케줄되는 것을 확인했습니다.

### 3-2. Softmax 의 행 최댓값이 클럭을 3배로 늘리고 있었습니다

```
run_Pipeline_fill    9.931 ns
```

`if (v[p*P+c] > mx[p]) mx[p] = v[p*P+c]` 를 P=8 레인에 순차로 쓰면 **한 사이클 안에서
8단 비교기 체인**이 됩니다. `softmax` 단독 9.931 ns 였고, **MHA 코어의 클럭도 이것이
정하고 있었습니다** (역시 9.931).

max 는 결합법칙이 성립하므로 트리로 바꿨습니다 — `log2(P)` 단.

| | 전 | 후 |
|---|---:|---:|
| `softmax` | 9.931 ns (100 MHz) | **2.405 ns (416 MHz)** |
| `mha_core` | 9.931 ns | **3.509 ns** |

**LayerNorm 의 합은 같은 모양인데 고칠 필요가 없습니다** — 툴이 정수 `+` 는 스스로
재결합하고, compare-and-assign 은 재결합하지 않습니다. 실측 2.399 ns.

### 3-3. 32레인이 2포트 테이블을 동시에 읽고 있었습니다

`softmax` 의 `normalise` 와 `gelu_stream` 의 `gelu_beats` 가 **II=16** 이었습니다.
`TP*P = 32` 개 레인이 각자 독립적으로 테이블을 인덱싱하는데 테이블은 2포트 메모리입니다.

엔트리 32개 × 16비트 = **64바이트**. 레지스터로 펼치면 공짜입니다.

| | II | LUT |
|---|---:|---:|
| `gelu_edge` 전 | 16 | 10,205 |
| `gelu_edge` 후 | **1** | 14,747 |

reciprocal 테이블(64엔트리 2벌)은 **행당 한 번**만 읽으므로 펼치지 않았습니다.

### 3-4. 상주 배열이 안 쓰이면 설계 전체가 상수 폴딩됩니다

첫 래퍼는 유닛을 `static` 에 담고 `compute` 만 불렀습니다. 한 번도 쓰이지 않는 static 배열은
0 으로 초기화되므로 `weight` 가 증명 가능하게 전부 0 이고, **MAC 배열이 통째로 사라졌습니다.**

```
rmu_proj   BRAM 0 · DSP 0 · FF 90 · LUT 463      <- 192x192 행렬곱입니다
```

결과처럼 보였습니다. 그래서 지금은 **모든 유닛이 페이로드를 포트로 받고 load 모드를**
가집니다. 상주 배열을 **읽는** 코드가 있으면 그것을 **쓰는** 경로도 있어야 하고,
아니면 리포트는 설계의 부재를 재고 있습니다.

## 4. 고치지 못한 것 — 측정으로 국소 수정이 기각된 건

### `push2d`/`pop2d` 가 MHA 코어 DSP 1,355 중 **960개**를 씁니다

연산이 하나도 없는 복사 루프입니다. `(r0 + p) * cols` 가 완전 언롤된 두 루프 안에 있고
`cols` 가 런타임이라, **레인마다 살아있는 37×39 곱셈기**가 생깁니다 —
`mul_37ns_39ns_75` × 32 × 5 DSP = 160 DSP, 인스턴스 6개.

**설계에서 가장 큰 곱셈기 사용처가 memcpy 입니다.**

국소 수정 두 가지를 시도했고 **둘 다 측정으로 기각**했습니다:

| 시도 | 결과 |
|---|---|
| 행 베이스를 레인 루프 밖으로 hoist | **DSP 1,355 그대로.** 곱셈이 어디 있느냐가 문제가 아님 |
| `cols` 를 템플릿 인자로 (호출부 15곳 전부 상수) | DSP 1,355 → 1,284 인데 **LUT 225,678 → 294,141**. 디바이스 230,400 을 넘김. 상수 스트라이드는 shift/add 트리가 되고, COLS 별 특수화가 복사 루프의 하드웨어 공유를 막음. **순손해** |

**결론은 국소적이지 않습니다.** 이 루프들은 단계가 `dataflow` 리전이 아니라 **완전 버퍼로**
이어져 있어서 존재합니다. 목표 설계에서는 FIFO 이고 복사 자체가 없습니다.

두 시도는 `hbtxr_mha_core.hpp` 주석에 남겼습니다 — 다시 하지 않도록.

## 5. `#pragma HLS dataflow` 를 넣지 않았습니다 — 이유

S9 계획은 SPEC §5-1 의 FIFO 깊이를 여기서 넣는 것이었습니다. **깊이는 실측했지만
`dataflow` 는 pragma 한 줄이 아니라 재구조화입니다.**

### 실측 FIFO 깊이 (`hls::stream` 최대 도달 깊이, V1)

| 유닛 | search N=64 | track N=16 |
|---|---:|---:|
| `layernorm` · `rmu` | 384 | 96 |
| `smu` | 128 | 32 |
| `softmax` | 384 | 24 |
| `patch` (F / E) | 512 | 256 |
| `mha` | 1,152 | 288 |
| **`mlp` · `block` · `backbone` · `top`** | **1,536** | 384 |

1,536 = `(64/4) × (768/8)` — MLP 은닉층 F=768 전체입니다. 비트로는 1,536 × 32레인 × 4비트
= **24 KB 한 개**.

**이 숫자는 dataflow 를 쓰지 **않을** 때의 비용입니다.** 생산자가 끝나야 소비자가 시작하는
현재 구성에서 필요한 깊이고, 실제 dataflow 리전에서는 겹쳐 돌기 때문에 훨씬 얕아집니다.
`mlp_core` 의 BRAM 136 이 대부분 이것입니다.

### `dataflow` 정규형을 지금 코드가 어깁니다

- `HbtxrMhaCore::run` 의 헤드 루프가 `qkv_buf` 를 **H=3 번 다시 읽고** `ctx_buf` 에
  **H 번 나눠 씁니다.** dataflow 채널은 생산자 1 · 소비자 1 이어야 합니다
- `x` 를 stage 1 과 stage 9(residual merge)가 **둘 다** 읽습니다 — 바이패스
- 헤드 루프 안에서 스트림이 매 반복 새로 선언됩니다

전부 고칠 수 있지만 **골든 대조를 다시 통과시켜야 하는 재작성**이고, §4 의 복사 루프 문제와
같은 작업입니다. 하나로 묶어야 합니다.

## 6. 남은 II 미달 — 전부 원인이 붙어 있습니다

| 어디 | II | 원인 |
|---|---:|---|
| `push2d` · `pop2d` | 16 | 단일 포트 메모리에 비트당 32접근. §4 |
| `load_out_load_in` (전 유닛) | 2 | reshape 된 배열에 **원소 단위** 적재 = read-modify-write. 보드에서는 M-AXI 가 8-wide 워드로 넣습니다 (S10) |
| `smu_ctx` 의 B 적재 전치 | 2 | `bt[j0+c][k0+p]` 가 dim 2 로 reshape 된 메모리의 서로 다른 행 8개에 씀 |
| `patch_f` windower | 4 | `lines[ky][...]` 를 32개 흩어진 주소에서 읽음 (Conv-E 는 2) |

`load_out_load_in` 은 **제가 측정용으로 붙인 경로**라 설계의 결함이 아닙니다. 다만 숫자는
기록해 둡니다 — qkv 적재가 **221,186 사이클 = 0.74 ms**, 블록 8개면 6 ms 입니다. 8-wide
로 넣으면 1/16 입니다.

## 7. 다음에 해야 할 것 — 우선순위는 측정이 정합니다

1. **`dataflow` 재구조화 + 복사 루프 제거** (§4 · §5). LUT 350% 와 DSP 960개가 같은 원인
2. **DSP 패킹 결정.** RMU 하나가 `TP×CIP×COP = 256` MAC 인데 DSP 160개 — 이미 1.6 MAC/DSP.
   4비트 곱을 DSP48E2 하나에 4개 넣거나 전부 LUT 로 내리면 4배. SPEC §2-A 의
   `TP`/`CIP`/`COP` 를 줄이는 것도 같은 축이고, **어느 쪽이든 지금 숫자가 근거입니다**
3. **V2 (csim) · V4 (cosim).** csim 은 툴 프런트엔드가 g++ 와 같은 값을 내는지 봅니다 —
   오늘 C++17 거부라는 실제 차이가 있었으니 가설이 아닙니다. **cosim 이 §5 의 FIFO 깊이가
   실제로 데드락하지 않는지 보는 유일한 층**입니다
4. **`HbtxrTop` · `HbtxrBackbone` 합성.** 합성 가능한 weight SOURCE 가 필요합니다 (S10)

